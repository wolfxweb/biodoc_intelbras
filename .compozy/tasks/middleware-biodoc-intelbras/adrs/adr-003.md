# ADR-003: SQLite para Armazenamento de Origens (Sources) Autorizadas

## Status

Accepted

## Date

2026-05-16

## Context

O PRD exige que o middleware mantenha um vetor de integrações disponíveis para validar o campo `source` do payload recebido, bem como verificar a validade do Token associado a essa origem. A escolha do armazenamento precisa equilibrar a baixa complexidade inicial com a capacidade de estender para novos parceiros (como requerido no PRD).

## Decision

Optamos por utilizar o **SQLite** embarcado na aplicação para armazenar as entidades de Sistema Parceiro (nome do source, hash do token, status). A API validará as requisições contra essa base de dados local utilizando SQLAlchemy ou queries diretas otimizadas.

## Alternatives Considered

### Alternative 1: Banco de Dados Relacional Externo (PostgreSQL/MySQL)

- **Description**: Levantar uma instância de banco de dados robusto via rede.
- **Pros**: Escalabilidade, alta concorrência.
- **Cons**: Adiciona dependência de infraestrutura desnecessária e complica a entrega do MVP.
- **Why rejected**: Excesso de engenharia (Overengineering) dado o volume minúsculo de dados (geralmente menos de 10 sources cadastrados).

### Alternative 2: Arquivos Estáticos / Variáveis de Ambiente

- **Description**: Definir as credenciais em um `.env` ou arquivo `sources.json`.
- **Pros**: Nenhuma dependência externa, super leve.
- **Cons**: Exige re-deploy da aplicação a cada adição de um novo sistema parceiro ou rotação de token.
- **Why rejected**: Engessa a operação e a escalabilidade administrativa definida no PRD.

## Consequences

### Positive

- Infraestrutura leve: arquivo do banco fica no próprio disco.
- Permite futuramente a criação de rotas CRUD internas para adicionar parceiros via API sem reiniciar o middleware.

### Negative

- Não é ideal se o middleware rodar em múltiplas réplicas (scale-out) sem volumes compartilhados persistentes.

### Risks

- Bloqueios de escrita (lock) no arquivo SQLite. *Mitigação*: Este banco terá 99.9% de operações de leitura (validação) e pouquíssima escrita, o que torna o risco irrelevante.

## Implementation Notes

Utilizar uma camada simples de cache em memória para a validação dos tokens/sources e revalidar com o SQLite para minimizar I/O de disco em cada chamada de webhook.
